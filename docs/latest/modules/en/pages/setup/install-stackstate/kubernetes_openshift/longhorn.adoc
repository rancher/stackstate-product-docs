= Run SUSE Observability on Longhorn
:page-languages: [en]
:revdate: 2026-09-08
:page-revdate: {revdate}
:description: Configure and operate Longhorn storage for SUSE Observability

This page describes the Longhorn decisions that are specific to SUSE Observability.
Use it together with the https://longhorn.io/docs/latest/[Longhorn documentation] for installation, capacity planning, monitoring, backup targets, and version-specific procedures.

== Before installation

Use SSD-backed disks that meet the xref:/setup/install-stackstate/requirements.adoc[SUSE Observability system requirements].
Provide at least three eligible Longhorn storage nodes and spread them across the failure domains that the installation must tolerate.
Configure Longhorn replica node and zone anti-affinity so that this separation is enforced, rather than only preferred.
Keep enough free capacity to rebuild all replicas from one failed or drained node.

Configure the Longhorn CSI `kubeletRootDir` for the Kubernetes distribution.
For example, RKE2 normally uses `/var/lib/kubelet`.

Do not use Longhorn replicas as a replacement for backups.
Configure xref:/setup/data-management/backup_restore/backup_enable.adoc[SUSE Observability backups] in external object storage and test the restore procedure.

== StorageClass strategy

The safest baseline is to use three Longhorn replicas for all durable SUSE Observability volumes.
This is the recommended starting point for both Non-HA and HA installations.

An HA installation can reduce replication traffic by using one Longhorn replica for selected services that already maintain independent application-level replicas.
This optimization makes the loss of one storage node a service-specific recovery operation: the application must rebuild the lost member after its PVC is replaced.
Use it only when that procedure has been tested.

[cols="1,1,1,3",options="header"]
|===
|Purpose |Longhorn replicas |Data locality |Use

|Durable
|3
|Disabled
|All durable Non-HA data. In HA installations, use for ClickHouse, Kafka, HDFS NameNodes, VictoriaMetrics, Workload Observer, settings, backups, StackPacks, and other state that cannot safely be recreated from an application peer.

|Application-replicated
|1
|Best effort
|HA installations only: Elasticsearch members, HDFS DataNodes, and ZooKeeper members. Losing the volume loses that member and requires application-level recovery.

|Transient
|1
|Best effort
|Temporary buffers and working data, such as vmagent and temporary component PVCs. Data in these volumes can be lost during a node failure.
|===

Keep Kafka on the durable class even in an HA installation.
Kafka topic replication can differ between topics, including internal topics, so the number of broker pods alone doesn't prove that every partition can survive the loss of a broker volume.

The following example creates the three classes.
Adapt the names and other Longhorn parameters to your environment.

[,yaml]
----
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: longhorn-durable
provisioner: driver.longhorn.io
allowVolumeExpansion: true
reclaimPolicy: Delete
volumeBindingMode: Immediate
parameters:
  numberOfReplicas: "3"
  dataLocality: disabled
  fsType: ext4
---
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: longhorn-application
provisioner: driver.longhorn.io
allowVolumeExpansion: true
reclaimPolicy: Delete
volumeBindingMode: Immediate
parameters:
  numberOfReplicas: "1"
  dataLocality: best-effort
  fsType: ext4
---
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: longhorn-transient
provisioner: driver.longhorn.io
allowVolumeExpansion: true
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
parameters:
  numberOfReplicas: "1"
  dataLocality: best-effort
  fsType: ext4
----

Set the durable class as the default for the chart:

[,yaml]
----
global:
  storageClass: longhorn-durable
----

For the optional HA optimization, add these overrides:

[,yaml]
----
elasticsearch:
  volumeClaimTemplate:
    storageClassName: longhorn-application

hbase:
  hdfs:
    datanode:
      persistence:
        storageClass: longhorn-application

zookeeper:
  persistence:
    storageClass: longhorn-application

stackstate:
  components:
    checks:
      tmpToPVC:
        storageClass: longhorn-transient
    healthSync:
      tmpToPVC:
        storageClass: longhorn-transient
    state:
      tmpToPVC:
        storageClass: longhorn-transient
    sync:
      tmpToPVC:
        storageClass: longhorn-transient
    vmagent:
      persistence:
        storageClass: longhorn-transient
----

See xref:/setup/install-stackstate/kubernetes_openshift/storage.adoc[Storage classes and customization] for the complete set of storage settings.
After installation, verify that every PVC uses the intended class and that every Longhorn volume is healthy.

== Understand the failure modes

[cols="2,3,3",options="header"]
|===
|Failure |Likely effect |Protection

|One node or disk holding a replica fails
|A three-replica volume becomes degraded but remains available. A one-replica volume becomes unavailable and its data is lost if the disk cannot be recovered.
|Spread replicas across independent nodes and failure domains. Restore the replica count before starting maintenance elsewhere.

|Failures exceed the available replica count
|Volumes become unavailable and may require restore. SUSE Observability components that depend on them become unavailable.
|Use three replicas for durable data, maintain failure-domain separation, and keep tested backups outside the cluster.

|A one-replica application member is lost
|The remaining application replicas may continue serving, but capacity or quorum is reduced. The lost PVC and member must be replaced and rebuilt.
|Use this layout only with the HA profile, monitor application health, and test the component recovery procedure.

|A disk fills or there is no destination for rebuilding
|Longhorn cannot restore the requested replica count. A second failure can then cause unavailability or data loss.
|Reserve rebuild capacity, alert on disk pressure and degraded volumes, and stop node maintenance until all volumes are healthy.

|A PVC is deleted
|With the `Delete` reclaim policy, the Longhorn volume can also be deleted.
|Restrict destructive access and rely on external backups for recovery.

|The cluster or an entire failure domain is lost
|Local replicas and snapshots can become unreachable together.
|Place replicas according to the required failure boundary and store SUSE Observability backups outside that boundary.
|===

== Maintain or rotate nodes

Operate on one storage node at a time.
Before each node, confirm that:

* SUSE Observability is healthy.
* All Longhorn volumes are healthy and have their expected replica count.
* Other nodes have enough storage and compute capacity for the workloads and replica rebuilds.
* A recent external backup is available.

For a short reboot or operating-system update:

. Cordon and drain the node with `--ignore-daemonsets`.
. If the drain is blocked, inspect Longhorn events and the replicas on the node. Do not force the drain past Longhorn's data-protection checks.
. Complete the maintenance and return the node.
. Uncordon the node and wait until Longhorn and SUSE Observability are healthy before proceeding to the next node.

Longhorn normally keeps reusable replicas during short maintenance.
The default `Block If Contains Last Replica` node drain policy prevents a drain from completing when the node contains the last healthy replica of a volume.
With one-replica classes, evict the replica before draining, or deliberately use `Allow If Last Replica Is Stopped` only for short maintenance where the same disk is expected to return.
The latter option loses the volume if the node or disk doesn't return.
Do not use `Always Allow` in production.
See the https://longhorn.io/docs/latest/maintenance/maintenance/[Longhorn node maintenance and drain policy guide].

For permanent node removal or replacement:

. Add replacement capacity before removing capacity.
. Disable Longhorn scheduling on the old node.
. Request replica eviction and wait until the node contains no replicas.
. Cordon and drain the node.
. Confirm that no volumes remain attached, then remove the node from Longhorn and Kubernetes.
. Wait for all volumes and SUSE Observability components to become healthy before removing another node.

Follow the https://longhorn.io/docs/latest/nodes-and-volumes/nodes/disks-or-nodes-eviction/[Longhorn replica eviction procedure].
Eviction rebuilds data over the storage network and can take a long time; schedule it as a storage-intensive maintenance operation.

== Operational checks

Alert on degraded or faulted Longhorn volumes, unschedulable replicas, disk pressure, node readiness, and replica rebuild failures.
Treat a degraded volume as reduced fault tolerance, not as a normal steady state.

Before and after maintenance, list the relevant resources:

[,bash]
----
kubectl -n longhorn-system get nodes.longhorn.io
kubectl -n longhorn-system get volumes.longhorn.io
kubectl -n <suse-observability-namespace> get pvc
----

Do not proceed to the next maintenance step until Longhorn has restored the expected replica count and the SUSE Observability workloads are ready.
