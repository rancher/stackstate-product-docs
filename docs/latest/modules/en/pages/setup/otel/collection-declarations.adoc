= Collect custom resources with CollectionDeclaration
:description: Select custom resources with namespace, label and field filters, grant read permissions, and check collection status
:page-languages: [en]
:revdate: 2026-11-19
:page-revdate: {revdate}

Use a `CollectionDeclaration` Kubernetes custom resource to tell the {stackstate-product-name} Agent which custom resources to collect for your integration.
The collector reads the declaration and updates collection without restarting its Pods.
You can select resources backed by a Kubernetes CRD; standard Kubernetes resources remain configured through the agent.

CollectionDeclaration requires agent chart version 1.7.69 or later.
Install or upgrade the agent before applying declarations, and ask your administrator to grant reads on the selected resources.

== Install the declaration API

The resource collector and declaration API are enabled by default when OTel is enabled.
To enable OTel, merge this override into your existing agent values:

[source,yaml]
----
otel:
  enabled: true
----

If you previously disabled `otel.k8sResourceCollector.enabled` or top-level `installObservabilityCrds`, set them to `true`.
The chart installs and upgrades the CRD as a Helm template and grants permission to read declarations and write their status.
Prometheus Operator CRDs keep their separate `otel.prometheusScraping.monitorCrds.enabled` opt-in.
For upgrade permissions and the installation opt-out, see xref:setup/otel/troubleshooting.adoc#collection-declaration-install-forbidden[CRD installation troubleshooting].

CollectionDeclaration is cluster-scoped.
Limit permission to create or change declarations to trusted administrators and integration installers.
A declaration writer can request export of resources that the collector can read, even when the writer cannot read those resources directly.
Declarations do not grant Kubernetes permissions.

== Select resources

This declaration selects the `payments-vm` VirtualMachine in the `payments` namespace when it has the label `app: checkout`.
Save it as `collectiondeclaration.yaml` and include it in the integration's Helm or GitOps configuration.

[source,yaml]
----
apiVersion: observability.suse.com/v1alpha1
kind: CollectionDeclaration
metadata:
  name: example-monitoring-payments-release-a
spec:
  resources:
    - group: kubevirt.io
      resource: virtualmachines
      namespaces: [payments]
      labelSelector:
        matchLabels:
          app: checkout
      fieldSelector: metadata.name=payments-vm
----

Give each declaration a name unique across the cluster.
Include the integration and release identity when several releases can install declarations.

[cols="1,3",options="header"]
|===
|Field |Meaning

|`group`
|Required exact API group, such as `kubevirt.io`.

|`resource`
|Required plural resource name. `"*"` selects all CRD-backed resource types in that exact group, including types installed later.

|`namespaces`
|Optional list of namespace names. Omit it to select namespaced resources across all namespaces. Omit it for cluster-scoped custom resources.

|`labelSelector`
|Optional Kubernetes label selector with `matchLabels` and `matchExpressions`. Supported operators are `In`, `NotIn`, `Exists`, and `DoesNotExist`.

|`fieldSelector`
|Optional Kubernetes field-selector string. It supports `=`, `==`, `!=`, and comma-separated AND clauses.
|===

Namespace, label and field filters within an entry must all match.
Separate entries and declarations add their results together.
Declarations also add to collection already enabled in the agent configuration.
A narrow declaration cannot remove objects selected by a broader declaration or the agent baseline.
Objects selected more than once are reported once.
The collector reads each selected type at its storage version.

Namespace-label selectors are unavailable in this API.
Custom field names must be exposed as selectable fields by the target CRD.
An unsupported field reports `Blocked` for the affected type; permitted types continue collecting.
Built-in resources and aggregated APIs without a CRD cannot be selected through declarations.

== Limit declaration watches

The collector limits the additional watches created by declarations.
The default is 256.
Administrators can change it through the agent chart:

[source,yaml]
----
otel:
  k8sResourceCollector:
    maxDeclarationWatches: 256
----

Each distinct resource, namespace, label selector and field selector combination needs a watch.
Several namespace names need separate watches.
Identical selections share watches, and watches already used by agent configuration do not consume this additional budget.
Wildcard selections can need watches for several resource types.

If a selected type needs more watches than the available budget, it reports `Blocked` with reason `WatchBudgetExceeded`.
Reduce the number of distinct namespace and filter combinations, remove unnecessary declarations, or increase the budget.
Collection resumes automatically when capacity becomes available.

== Check collection status

In SUSE Observability, open *Agent > Collection Declarations* to inspect declarations and their current collection feedback.
This overview includes collection declarations; selections from the agent YAML configuration are outside its scope.
Declarations also appear under *Kubernetes > Custom Resources*.

[source,shell]
----
kubectl get collectiondeclarations example-monitoring-payments-release-a -o yaml
----

Compare `status.observedGeneration` with `metadata.generation` before reading the results.
The `Ready` condition is true when all selections are active.
Each entry in `status.resources` identifies its selection with `selectionIndex`.
Index `0` is the first entry in that generation's `spec.resources`.

[cols="1,3",options="header"]
|===
|State |Meaning

|`Active`
|Initial observation succeeded. An empty result is valid.

|`Pending`
|The collector is waiting for an API or a successful observation and will retry.

|`Blocked`
|A permission, policy or selection problem prevents collection. Read the entry's `reason` and `message`.
|===

A wildcard selection can be blocked while other types it resolves continue collecting.
Status describes collection in the agent; it does not confirm delivery to SUSE Observability.
See xref:setup/otel/troubleshooting.adoc#collection-declaration-troubleshooting[Troubleshoot CollectionDeclaration] for recovery steps.

During a temporary API or permission failure, the collector keeps the last observed objects for an unchanged selection.
Changing a selection or deleting its declaration stops reporting its previous objects unless another declaration or agent setting still selects them.
An administrator deny or exceeded watch budget also stops reporting the affected objects.
Previously reported data follows {stackstate-product-name} retention.

== Read custom resources with restricted RBAC

With `otel.k8sResourceCollector.rbac.useWildcard: true`, the collector has `get`, `list`, and `watch` permissions on all API groups and resources.
Administrator collection denies still apply.

With `useWildcard: false`, an administrator can manage separate read-only Roles or ClusterRoles and bindings.
The collector does not create permissions from declarations.
The agent chart supplies CRD discovery, declaration reads and declaration status writes.

The following example uses Helm release `observability-agent` in namespace `observability`.
Its collector ServiceAccount is `observability-agent-k8s-resource-collector`.
Replace the release name, namespace and identity with those from your installation.
It assumes your cluster has `widgets` and `reports` custom resources in API group `example.com`, with no existing integration preset.

Merge this override into an installation with the OTel resource collector and declaration consumption enabled:

[source,yaml]
----
otel:
  k8sResourceCollector:
    rbac:
      useWildcard: false
----

An administrator adds these read grants through the installation's Helm or GitOps configuration:

[source,yaml]
----
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: observability-agent-example-read
rules:
  - apiGroups: ["example.com"]
    resources: ["widgets", "reports"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: observability-agent-example-read
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: observability-agent-example-read
subjects:
  - kind: ServiceAccount
    name: observability-agent-k8s-resource-collector
    namespace: observability
----

The integration can then request those types across namespaces:

[source,yaml]
----
apiVersion: observability.suse.com/v1alpha1
kind: CollectionDeclaration
metadata:
  name: example-payments-release-a
spec:
  resources:
    - group: example.com
      resource: widgets
    - group: example.com
      resource: reports
----

An identity permitted to impersonate the collector can check each required verb:

[source,shell]
----
for resource in widgets reports; do
  for verb in get list watch; do
    kubectl auth can-i "$verb" "$resource.example.com" --all-namespaces \
      --as=system:serviceaccount:observability:observability-agent-k8s-resource-collector
  done
done
----

Each result should be `yes`.
These checks verify authorization, not successful API observation or backend delivery.
Use declaration status to check collection.
For missing permissions or delayed recovery, see xref:setup/otel/troubleshooting.adoc#collection-declaration-troubleshooting[Troubleshoot CollectionDeclaration].

=== Limit reads to a namespace

To limit access to `payments`, retain the ClusterRole and use this RoleBinding instead of the ClusterRoleBinding above:

[source,yaml]
----
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: observability-agent-example-read
  namespace: payments
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: observability-agent-example-read
subjects:
  - kind: ServiceAccount
    name: observability-agent-k8s-resource-collector
    namespace: observability
----

Add `namespaces: [payments]` to both resource entries in the declaration.
This makes the collector issue namespace-scoped LIST and WATCH requests.
A namespace RoleBinding does not authorize an all-namespaces request.
For permission checks, replace `--all-namespaces` with `--namespace=payments`.

RBAC grants are additive.
Remove any broader bindings if the intention is to limit the collector to this namespace.
A wildcard declaration may discover other types not authorized by these exact resource grants.
Use the two explicit resource entries when only those types are permitted.

== Restrict collection

Administrators can block a resource type in the agent values:

[source,yaml]
----
otel:
  k8sResourceCollector:
    deniedObjects:
      certificates:
        group: cert-manager.io
      virtualmachines:
        group: kubevirt.io
----

Each entry pairs an exact plural resource name with an exact API group.
It blocks that type across namespaces and API versions, including baseline custom-resource discovery and declarations.
Matching explicit `objects` entries fail configuration validation.
A deny does not revoke Kubernetes read permissions.

Adding a deny stops further collection and export.
Previously exported data follows downstream retention.

== Installation and migration

Install the agent before the integration.
An integration chart that checks for the CollectionDeclaration API may omit its declarations when the API is absent.
Installing the agent later does not rerender that integration.
Upgrade the integration release after the API becomes available.
Existing integration flags and declarations can coexist.
Keep existing integration flags enabled when adding declarations.
Declarations cannot replace the Pod or other standard Kubernetes resource selections an integration flag may provide.

Upgrade to agent chart version 1.7.69 or later before using declarations.

=== CRD lifecycle

The agent chart installs and upgrades the CollectionDeclaration CRD when OTel is enabled and top-level `installObservabilityCrds` is `true`.
These are the default lifecycle settings:

[source,yaml]
----
installObservabilityCrds: true

otel:
  k8sResourceCollector:
    collectionDeclarations:
      keep: true
----

`keep: true` preserves the CRD and declarations on uninstall or when disabling CRD installation.
It does not prevent CRD schema upgrades.
With `keep: false`, Helm can delete the CRD and all its declarations, including those created by integration charts.

Use `installObservabilityCrds: false` for an externally managed CRD or an additional agent release.
The chart stops installing and upgrading Observability CRDs.
The collector retains permission to read declarations and write status, and existing YAML collection continues.
If an existing release used `keep: false`, first upgrade it with `keep: true`, then disable installation in a second upgrade.
Changing both values together does not protect the CRD because Helm uses the previous release's keep annotation when removing it.

`otel.k8sResourceCollector.enabled: false` stops the collector without disabling CRD installation.
Helm's `--skip-crds` option does not skip this CRD because it is installed as a template.
Prometheus Operator CRDs retain their separate installation and keep flags.
One release should own the cluster-wide CollectionDeclaration CRD.

Deleting a declaration removes its contribution; other declarations and agent settings may continue collecting the same resources.

=== Adopt an existing CRD

A retained CRD keeps its previous Helm release ownership.
Installing under another release name or namespace can fail the ownership check.
Before adoption, verify that the existing schema is compatible and that the previous release no longer manages the CRD.
Then assign ownership to the intended release:

[source,shell]
----
kubectl label crd collectiondeclarations.observability.suse.com \
  app.kubernetes.io/managed-by=Helm --overwrite
kubectl annotate crd collectiondeclarations.observability.suse.com \
  meta.helm.sh/release-name=<release-name> \
  meta.helm.sh/release-namespace=<release-namespace> --overwrite
----

Permanent CRD removal also deletes its declarations.
